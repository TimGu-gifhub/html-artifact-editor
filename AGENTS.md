# Repository instructions for AI contributors

## Current scope

This is HTML Artifact Editor, a local-first visual text correction tool for existing HTML. HAE-001/002 add the toolchain and read-only project previews; HAE-003/004 verify static mapping and byte patches. HAE-005 experiments connect drafts, isolated Text changes, exclusive copies, pending input and trusted IPC through a unified Main window session with document/view transitions and close protection. HAE-008 adds explicit directory grants, protected entry changes and bounded resource diagnostics to that Main session. The normal app still has no product editing/diagnostics UI, overwrite saving or recovery. Read README.md, PRD.md, ARCHITECTURE.md, docs/PATCH_SPEC.md and the target Issue before implementation.

Human-readable project documentation is primarily Simplified Chinese. Keep identifiers and API contracts concise in English. Do not copy private conversations, user paths or unrelated project data into this public repository.

HAE-010 connects its Main/platform save transaction to an optional Workspace save port and narrow trusted IPC: private cooperative lock, verified backup/candidate, explicit Windows ReplaceFileW commit, result journal and fresh baseline/mapping. The file version is captured at document open. Preparing/cancelling never replaces HTML; prepared is not saved. Failure/unknown or failed rebind retains evidence and blocks blind retry; cleanup warnings do not turn a verified save into failure. Read docs/SAVE_PREPARATION.md and docs/WORKSPACE_SESSION.md before extending it. `npm run test:storage` runs real filesystem/native helper tests under Electron's bundled Node; `npm run test:save-session` exercises the production transport in real Electron windows on Windows. Neither is normal product UI or recovery acceptance. The Windows helper builds from C# source with the local .NET Framework compiler; never commit its executable or generated sidecars.

Main `prepareRestore` can now restore a verified backup through the same transaction, backing up the currently authorized file first. It uses exact backup bytes and a v2 intent linking the source backup; ordinary v1 records remain readable. It does not replay drafts, recover historical ACL/ADS or release stale locks. Current version/target checks, backup revalidation and explicit commit remain mandatory.

Optional Workspace backup restoration now exposes only current-document metadata and an exact transaction/hash reference through trusted listBackups/restoreBackup. Read docs/BACKUP_RESTORE.md before extending it. Main requires a separate bound confirmation, rejects composing/unapplied/dirty input, freezes edits and drains the exact latest clean checkpoint before replacement. The proof retains the backup version captured before review. Verify the committed file and fresh mapping around native installation before publishing backup-restored; whole-backup restoration starts fresh clean history and never migrates old Text offsets/lineage. Failure/unknown or failed rebind retains the frozen old session and evidence. Renderer loss after commit starts cannot revoke reconciliation. Normal product backup/confirmation controls and live failure resolution remain unimplemented.

Main prepareSaveRecovery can explicitly resolve a complete interrupted Save's lock after reacquiring the profile and excluding active documents/storage operations. Read docs/SAVE_RECOVERY.md before extending it. A new keep-current decision binds the newly authorized current version; a read-only Windows guard excludes write/delete handles while Main seals the decision and removes only the exact old lock. Preserve baseline-matches, committed-matches, candidate-on-disk and conflict distinctions; a resolution receipt is never a SaveCommit or authority to replay history. Preserve the complete original transaction, backups, candidates and sidecars. Partial/corrupt receipts block writes and recovery, and their transaction anchors must survive future cleanup. Empty/unclassified locks, incomplete transactions, live-window state and generic sidecar cleanup remain unresolved. There is no renderer recovery method.

HAE-011 adds logical Text checkpoints and an optional Workspace persistence port; read docs/DRAFT_CHECKPOINTS.md before extending it. Confirmed changed Apply enqueues a frozen candidate, keeping one active write and only the latest pending candidate. Background durability state must not invalidate input revisions. Failures stop automatic writes; trusted retry targets the latest current document revision. Save and close wait for active persistence; only Save writes HTML. Recovery rebuilds fresh source ranges and verifies file identity/hash; a matching committed version prevents duplicate replay. Main catalog/latest selection uses revisions and cannot fall back past a newer incomplete or clean point. Main retirement appends a bound marker only after an explicit discard or verified copy decision, drained writes and frozen edits; it does not delete evidence or free quota. Corrupt/unclassified retirement evidence blocks recovery. Checkpoints and saves share one private directory, lock and quota. Never remove a retirement anchor while older session records remain.

Workspace departure now freezes InputController in leaving, drains persistence, stages native activation, confirms the authorized marker, then publishes the new document. Pre-marker cancellation/activation failure releases the old input; retirement failure/unknown keeps it frozen with source/candidate evidence and lastDeparture.requiresReview, never force-closing or blindly retrying. A clean departure after edits requires the exact latest return-to-baseline checkpoint. Renderer loss after a marker starts cannot revoke the existing decision; Main reconciles it, preserving evidence if view activation also becomes uncertain.

Optional Workspace recovery now lists safe metadata and reauthorizes file/directory selection before restoring the verified latest dirty checkpoint into a fresh unpublished mapping. Batch Text restoration is fresh-only; it grants no page API or offset authority. Recheck the source and selected record around native installation. Keep a separate checkpointSessionId for the resumed durable sequence and a new current.id for UI commands; seed persistence without a duplicate write. Persistent document preparation requires Electron profile ownership, and private-directory/session ownership excludes duplicate windows; do not release ownership while document teardown is uncertain. Detach the chooser abort signal only when preparation transfers ownership to Workspace; the document owns its mapping lifetime. Normal product entry, recovery failure resolution, cross-session/failure cleanup and product history/Diff controls remain unimplemented. `npm run test:recovery` covers real Electron recovery and process ownership; it does not prove product or unavailable-platform acceptance.

HAE-011 now provides source Diff through a bounded Worker and trusted Workspace readDiff, with an optional revision/hash review on Save. Read docs/SOURCE_DIFF.md before extending it. Main validates worker slices, coalesces reads and rejects stale results/reviews. Document teardown waits for Diff termination and persistence; unconfirmed termination prevents more workers and successful cleanup. Product Diff/history controls remain unimplemented; Main history and cross-save Undo are described below. `npm run test:source-diff` exercises real Electron transport and reviewed Windows Save; it is not product acceptance.

Workspace recovery can now reconstruct a saved v2 history after a verified native commit but before its clean checkpoint became durable. Main prepareRecovery binds the exact current file version and one matching intent/commit journal, rebases history without replay, then seals a new clean sequence before installation. Hold ownership of both the requested and continuation sessions until confirmed teardown. Existing records bound to the saved file version, including incomplete or retired continuations, block fallback through the old saved entry; never delete that evidence to retry. Installation/cancellation failures retain any new private point. Legacy v1 saved points remain unavailable, and missing/ambiguous commit evidence or stale locks cannot authorize this recovery. Read docs/DRAFT_CHECKPOINTS.md for the precise boundary; product recovery/failure resolution and cross-session/failure cleanup remain unimplemented.

Owned v2 checkpoint writes now compact superseded complete points in the same session under the existing lock. Read docs/CHECKPOINT_COMPACTION.md before extending this. Retain the latest two unambiguous complete revisions, incomplete/invalid/ambiguous evidence, every other session and every save backup. Seal a bounded compaction.json before deleting exact verified files and empty UUID directories; never recurse or use a journal path as authority. Revalidate both retained points and the owned lock/journal before each removal. Interrupted/unknown cleanup retains available evidence and lock, blocks recovery/retry, and never turns a verified checkpoint into a claim that newer memory edits are durable. No automatic restart of deletion or general stale-lock release exists; explicit scoped compaction recovery is described below. Retirement anchors and continuation evidence must survive future broader cleanup; current compaction does not remove them.

Main now offers explicit recovery of an interrupted checkpoint compaction through prepareCompactionRecovery. Read docs/COMPACTION_RECOVERY.md before extending it. Require the current Electron profile and a direct private child directory, no active documents/storage operations, a newly authorized unchanged source, two complete retained points and exact lock/journal evidence. Prepare/cancel are read-only. Before further deletion, seal a durable copy of the old journal/lock; after verifying all obsolete directories are absent, seal completion before removing the original journal and exact old lock. Repeated commit shares one result; a new attempt revalidates everything. A completed receipt permits continuation after journal removal, but partial/corrupt receipts block ordinary writes and recovery. Receipts stay in the same quota; never ignore them or prune incomplete evidence to unlock. This is not a general Save/retirement lock resolver or live-document unfreezing API, and no renderer method exists. Native profile checks and production Workspace recovery are covered separately from lower-level storage tests.

## Invariants

HAE-011 core history now provides prepared/confirmed transitions, logical Undo/Redo, savepoint rebasing and strict private record round-trips. Read docs/HISTORY.md before extending it. SourceIndex.lineage is Main/private history data, not a renderer capability. Reparse both sources and verify the full tree and every literal source gap before reconstructing an emptied Text at a fresh zero-length range; never accept an old offset or strip lineage to bypass verification. Parser/Draft/Diff workers rebuild this proof. Main must confirm Preview application before history commit, and verify the actual saved version before rebasing. Unknown outcomes retain old history and candidate evidence. Main Workspace history commands and v2 complete-history checkpoints are now connected; legacy v1 checkpoints still reject lineage with DRAFT_HISTORY_UNSUPPORTED before disk writes. `npm run test:history` verifies core/worker/native-save and isolated Preview integration, not product UI or manual acceptance.

Main createPreviewMapping can now accept private lineage through the bounded parser Worker. Only the verified current tree and proven empty positions reach the isolated preload; original bytes and the private lineage record stay in Main. The registry first matches the entire real DOM with the missing Texts omitted, checks all parent/sibling objects and support limits, accounts for each inserted empty Text's exact childList record, then matches the full augmented tree before publishing ready. An augmented tree alone is not installation authority. Main applyHistory is selection-independent but requires an exact mapping revision, known Text/old value, idle edit guard and one canonical prepared change. Confirmed application clears selection and advances the mapping revision; stale/rejected requests do not move logical history, and unknown outcomes invalidate further writes. This is a private mapping primitive; DraftSession/InputController and Workspace commands now own candidate/history confirmation and pending-input rules.

- Preserve the original file bytes outside verified text patch ranges. Never save a serialized whole DOM/AST as a shortcut.
- Never locate a write using only a selector, global text replace, or page-supplied offsets/paths.
- Reject unsupported/ambiguous source mappings. The MVP guarantees only supported static text; JavaScript interaction preview is read-only.
- Core modules must be pure and OS-independent. OS-specific code belongs to platform/storage adapters.
- Keep trusted editor UI separate from untrusted Preview. No Node integration, broad IPC bridge, arbitrary file access or shell access in user content.
- Keep offline policy, sandbox, context isolation, web security, CSP and IPC validation intact.
- Apply/cancel changes affect drafts; only explicit Save or separately confirmed whole-backup restoration writes the HTML. Failure or unknown outcome must preserve drafts and source/recovery evidence.
- Do not bypass backup, conflict detection or recovery to make a demo appear complete.
- Never add layout editing, structural DOM edits, framework source editing, AI services or network features without an explicit scope change.

Main history runs through a bounded Worker and keeps only confirmed plans. Trusted history commands bind document/input/draft revisions; composing, unapplied input and pending native intents reject them. Release a clean edit guard only after candidate preparation and reject intervening mapping changes. v2 checkpoints freeze candidate, full HistoryRecord and origin bytes together; verify the entire logical chain/source proof and all hashes before recovery. Clean v2 points can restore Redo without replaying an older dirty point. Legacy v1 recovery has no fabricated history. Verify the actual committed file before rebasing, then persist the new clean point; committed-but-unrebound v2 recovery follows the exact journal/continuation checks above and must not replay a saved draft. Close drains history workers, Diff and persistence before releasing document ownership. Read docs/HISTORY.md and docs/DRAFT_CHECKPOINTS.md before extending these contracts.

## Frontend model assignment

- User requirement: frontend design and implementation must use the latest officially released Kimi model available for the task. The verified baseline on 2026-09-08 is Kimi K3 via Kimi Code, using the full CLI alias `kimi-code/k3`.
- This applies to product UI components, styling, interaction states, accessibility and frontend portions of mixed tasks. Keep React/TypeScript as the application stack; Kimi is a development tool, not an application runtime dependency.
- Before each frontend task, check official model information and the configured/available Kimi Code models. Record the verification date, CLI version, actual alias/model and relevant settings; keep that choice stable within the task. Do not silently substitute an older model or another provider when the selected model is unavailable.
- Kimi owns the bounded frontend change. The primary development agent owns core/source mapping, file transactions, security, integration and independent review. Mixed tasks must define the frontend files and contracts before handing off; do not grant the UI authority to change protected core boundaries.
- Retain one writer at a time unless parallel work is explicitly arranged. Actual Kimi execution must be recorded before claiming that Kimi produced a frontend change; this planning amendment does not itself run a frontend implementation task.
- Follow the detailed model selection and handoff policy in docs/AI_WORKFLOW.md.

## Working process

1. Inspect current worktree, target Issue, dependencies and existing code. Preserve unrelated and parallel changes.
2. Work on one bounded task at a time. Default to one writer; do not launch parallel agents unless explicitly arranged by the user.
3. State the concrete behavior to deliver, implement a small slice, then run checks appropriate to its risk.
4. UI work must follow docs/PRODUCT_DESIGN.md, including IME, focus, drafts, cancel, async revisions, errors and responsive limits. Obtain a selected visual target before implementing the product UI.
5. Verify a runnable result and inspect the diff. Mark manual or unavailable-platform checks as pending, never passed.
6. Update relevant specs when contracts change. Summarize behavior, evidence, limitations and next task.

## Publishing and privacy

The initial public MIT repository creation was explicitly requested. Later publication must follow the authorization for that task; this file does not grant ongoing permission to publish any arbitrary changes, artifacts or user data.

Fetch current refs, check branch/worktree state, stage only intended paths, inspect staged diff, run applicable gates, and verify remote/local commit parity after an authorized push. Do not force-push, disable certificate validation, or use broad staging to sweep unrelated work.

Before every GitHub push, PR or release, check the AI tools, models and providers actually used for the change. If a new tool, model/version or provider has participated, update README.md's "AI 辅助开发与致谢" in the same change with verified names/versions, the corresponding company and contribution scope, thanking the company and models. Retain prior acknowledgements; configuration or planned use alone is not actual participation, and unknown model versions must not be guessed. Follow the attribution rules in docs/AI_WORKFLOW.md.

Never commit secrets, user documents, private snapshots, backups, recovery logs, signing certificates or generated installers. Keep LICENSE notices and third-party license obligations intact.
