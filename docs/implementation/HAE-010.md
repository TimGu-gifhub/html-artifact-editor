# HAE-010 实施记录：Windows 保存事务与会话

日期：2026-09-09。对应 [Issue #10](https://github.com/TimGu-gifhub/html-artifact-editor/issues/10)。第一阶段交付准备证据；第二阶段增加 Main 显式 Windows 提交、结果回读和提交/未知判断；第三阶段连接 Workspace 显式保存与新基线；第四阶段增加 Main 显式备份恢复事务。正常应用和恢复向导尚未接线。HAE-010 与 M2 保持未完成。各阶段保留当时范围与计数，最新进度见文末。

## 行为与合同

源文件打开时固定字节、目录链、文件身份及纳秒时间戳，准备前重复核验。Main 私有存储使用同一目录的全局独占锁，备份和候选通过完整句柄写入、sync、独立回读/hash 与前后身份检查；准备和取消记录均独占创建。失败保留部分证据；正常取消仅释放本调用仍拥有的锁。

重启 scan 发现完整/部分记录与遗留锁；inspect 校验 schema 和字节关联，再比较 Main 重新授权的目标。旧基线、候选已在磁盘、外部冲突和不可读状态分开，不自动覆写或解除遗留锁。记录不含绝对路径，不从记录中恢复路径权限。细节与预算见 [保存准备合同](../SAVE_PREPARATION.md)。

没有产品组件、样式、恢复界面或 Kimi 前端变更。候选语义仍由已有源码映射/Patch 核心负责；本阶段只验证和保存其冻结字节。所有文件样例自行创建，未使用业务资料或 GitHub CI。

## 第二阶段：实际 Windows 替换与提交记录

基线为 `3405d9e227d3dd40c05c05e696751c587922d526`。增加 [Windows 适配器](../../src/platform/windows-replacement.ts)、[有限协议 C# 助手](../../src/platform/windows/ReplaceHelper.cs) 与 Main commit：私有证据再次校验 → 同目录独占候选 → 目录/源句柄检查 → replacing 日志 → ReplaceFileW → 新目标与移走原件复核 → Main 独立回读 → committed 日志 → 按持有句柄清理旧文件副本。原始私有备份和候选不删除。

重复 commit 共用同一结果；启动后的失败/未知不允许 cancel 或盲目重试。明确提交后清理失败仍报告 committed + cleanupPending。重启把 replacing/committed、候选仅在磁盘、当前版本与已提交版本不同分别处理；记录不携带目标绝对路径或可复用写权限。完整顺序、资源上限与残余竞态见 [保存事务合同](../SAVE_PREPARATION.md)。

Windows 使用本机 .NET Framework C# 编译器生成 helper，不下载新的运行依赖、不提交可执行文件。ReplaceFileW 不忽略 ACL 合并错误。对旧式 ACL 的继承位转换采用明确记录的兼容恢复，再复核 ACE 字节和控制位；权限不足则拒绝或保留未知结果。该路径使用微软标记 obsolete 的 SetFileSecurityW，仅用于还原原 DACL，后续平台替换方案需保留这一兼容性证据。没有产品前端文件或 Kimi UI 变更。

## 第三阶段：显式保存与窗口新基线

基线为 `aadef6e0ed483088c345aca655a60885848fec81`。增加 [Main 保存协调器](../../src/main/storage/original.ts)，通过 WorkspaceSession 的可选端口与生产 preload 暴露 `save(documentId, stateRevision)`。Main 在打开文件时固定源版本；显式保存已应用候选，文件与 committed 记录核验后重新解析和映射，沿原项目根安装新文档。只在这些步骤完成后报告 saved，旧文档/节点 ID 失效，后续保存使用新字节基线。

保存过程拒绝后到输入、重复 Save、Open 和原生关闭。未应用输入或组合态不会隐式应用；无变化不创建事务。已提交但新视图/映射无法安装时，保留旧源/候选和事务，报告 rebase-required。未知结果不盲目重试；已确认文件与新基线但清理失败，仍显示保存成功及清理警告。UI 在替换前失效会取消准备；在开始提交后崩溃，Main 继续确认并重建，重载只读取当前状态。

本阶段没有产品组件、样式或 Kimi UI 实施。真实 Electron 测试使用无控件的可信传输页面；所有报告/HTML/资源/私有存储自制并被忽略。接口及状态见 [统一窗口会话](../WORKSPACE_SESSION.md)。

## 第四阶段：备份恢复再次保护当前文件

基线为 `906ecf1ba7d16e15d73f233469b359b3d8656f0a`。Main 的 `prepareRestore(source, transactionId)` 从完整有效事务中取得经验证的原始备份，绑定来源字节、intent hash 和目录/文件版本；针对 Main 重新授权的当前源文件，先创建并独立回读新的“恢复前备份”，再准备旧备份的完整字节。明确 commit 使用同一 Windows ReplaceFileW、结果校验和 journal 流程，取消、失败/未知与清理规则不变。

普通 intent 的 v1 继续读取；恢复 intent 使用 [v2 schema](../../src/contracts/save-record.ts)，增加 `restoreOf: {transactionId, intentHash}`，不保存绝对路径或强制权限。恢复产生的新备份可以再次显式恢复，原有证据不删除或消费。Main/进程重启只读检查不自动执行恢复；现有锁也不会因此解除。完整语义见 [保存与备份恢复合同](../SAVE_PREPARATION.md)。
