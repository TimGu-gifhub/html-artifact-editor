## 第一阶段交付

从已验证的净 Patch 导出有限逻辑 Text 意图，保留原始基线；恢复时重新解析、核验来源，再生成新字节位置与完整候选。检查点由不可覆盖的 record/baseline/complete 三文件组成；每步句柄写入、sync、回读，之前的完整点不被失败覆盖。相同修订可确认重试，旧修订拒绝，清理警告与持久化结果分别报告。完整合同见 [草稿检查点](../DRAFT_CHECKPOINTS.md)。

草稿与保存使用同一私有目录、active.lock、每目标合计 20 份记录和总计 200 MiB 配额。两类扫描只列各自记录；不自动清理、解除遗留锁或选取旧草稿回放。重启恢复需 Main 重新授权文件并验证完整身份/hash；匹配实际 committed 版本的检查点拒绝重复应用，只有候选字节相同则保留未确认状态。

本阶段没有产品组件或样式，没有 Kimi UI 实施，也没有 GitHub CI。所有源文件、私有记录和进程故障现场均自制并位于忽略目录；公开仓库只含代码、测试和说明。

## 第二阶段：Apply 异步持久化与窗口协调

基线为 `8a2d9808a9380c90b246ecfc6e2ef817860e163a`。Workspace 的 Main checkpoints 端口为每份文档建立队列，确认变化的 Apply 固定候选后异步写入；只保留一份正在写的候选和一份最新待写候选。no-op、验证拒绝或 Preview 结果未知不会冒充确认修订。零净变化仍写入新的原基线检查点。

current.persistence 显示准确的草稿/活动/待写/已确认修订，后台完成通知不推进 InputSnapshot 的版本。失败保留已应用文字和最后确认点，停止自动写入；可信 retryPersistence 只允许当前文档的最新修订，没有路径或候选参数。Save 在输入互斥后等待当前私有写入，才竞争同一存储锁；文档关闭也等待队列。成功 Save 后的新文档使用新基线和独立队列。

新增 [六项队列单元测试](../../tests/unit/draft-persistence.test.mjs) 与 [一项 Apply 行为](../../tests/unit/draft-session.test.mjs)：慢写合并、旧完成不冒充最新版本、故障后显式重试、清理警告、错修订/hash/ID 或拒绝的响应、关闭排空和归零。既有 IPC schema 测试扩充错误文档/修订及禁止文件权限字段。
