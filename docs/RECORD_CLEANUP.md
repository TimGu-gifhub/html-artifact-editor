# 本地记录清理合同

日期：2026-09-10。对应 HAE-011 第十六阶段，依赖 [持久化启动](PERSISTENT_STARTUP.md)、[草稿检查点](DRAFT_CHECKPOINTS.md)、[保存事务](SAVE_PREPARATION.md) 与 [产品中断检查](INTERRUPTION_WORKFLOW.md)。

## 用户可见行为

在尚未打开文档的工作台选择“更多操作 → 清理本地记录”。应用检查当前 profile 内全部草稿、撤销历史和应用备份，再由 Main 原生对话框显示数量、大小及永久删除提示，默认选择取消。确认后删除这些私有记录，释放原有记录额度；项目 HTML、CSS、PDF 和附属文件不变。清理后的编辑、复核、备份保存仍走原有完整流程。

当前不支持挑选部分会话或备份保留。记录可能含有尚未保存的修改，删除后无法从应用恢复。已打开任何文档时不能清理：先通过已有保存或另存/离开流程保留需要的内容，正常重启后、打开文档前操作。清理不替用户丢弃当前草稿，也不隐式保存 HTML。

原生确认中的“含修改的草稿记录”是私有目录元数据，不能证明相应改动尚未写入当前 HTML。中断后显示上次确认时的原清单及原始字节数，部分记录可能已删除；取消表示本次没有继续删除，不表示上次删除已撤销。

## 权限和进入条件

唯一目录是已由持久化工厂认领的 `userData/workspace-records`。Main 要求当前 Electron profile 锁，并比对启动时捕获的完整私有目录身份链；不能通过替换为一个新的空目录绕过旧证据。目录不由 renderer 选择。

Main 维护所有权排除活动文档、检查点、Save 与其他存储操作。工作区须为空闲、无当前文档、无清理/保存/离开未知结果。已接受命令使用精确工作区修订；过期请求在检查前被拒绝。来源 HTML 不需要为清理重新授权，因为该操作没有项目写入端口。

可信桌面 IPC 只接收严格的 `{ kind: 'clear-records', stateRevision }`，只允许主窗口；多余的路径、文件清单、审查 ID 或删除决定不被接受。UI 收到的是计数、大小、阶段和脱敏结果，不能取得 manifest、源码或文件路径。Preview 继续没有桌面、Workspace、Node 或文件能力。

## 检查与确认

[清单检查](../src/main/storage/cleanup-inventory.ts) 先捕获每个文件的身份、完整字节 hash 和大小，再验证同一批字节的语义，最后重新比对所有 proof。它包括全部完整草稿点及历史，不只检查最新点；旧修订冲突、旧 origin 损坏、部分记录也会拒绝。已退役会话与完整保存记录可纳入清理；Save/检查点清理的处置凭证必须符合既有格式、hash 和完成证明。

`active.lock`、未完成的 `compaction.json`、未知文件、损坏/不完整记录、未处置的 prepared/replacing Save 都阻止新清理。已完成明确处置的旧 Save，以及 v2 abandoned 准备记录，可以随其原始事务一同纳入。本功能不是通用锁解除器；需要先用已有的独立中断检查处理其支持的情形。

检查及取消均不新增、改写或删除私有记录。Main 为本次原生确认生成新的随机 reviewId，只接受匹配 ID 的明确清理或取消决定；默认按钮和 Escape 均为取消。失效决定与确认前 renderer 丢失不会开始删除。

## 删除协议

[Main 存储计划](../src/main/storage/record-cleanup.ts) 在首次删除之前，独占创建、同步并回读验证固定 `record-cleanup.json`。该文件保存版本、随机清理 ID、根目录身份、原始计数、有限的 UUID 子目录及固定文件名 proof。它不包含可执行路径、项目源码或通用递归能力。

manifest 是这次删除的持久化恢复门槛。它存在时，普通 Save、检查点、目录 catalog/恢复流程按既有未知记录规则停止；当前产品也通过 Main maintenance 状态阻止其他命令。没有添加另一种 active.lock，也不会删除或重写已有的 active.lock。

删除顺序固定：

1. 先处理没有退役标记的 UUID 记录目录，再处理含退役标记的目录。因此旧会话点先消失，退役锚点不会留下可以被恢复的旧序列。
2. 每个目录只删除预先列明且已核验的固定文件名，然后以非递归 rmdir 删除确认为空的同一目录。
3. 所有原始记录目录消失后，才删除完整 Save/compaction 处置凭证。
4. 所有清单项均确认不存在后，最后删除本次 manifest，并再次检查私有根为空及 profile 所有权。

[平台删除适配器](../src/platform/record-removal.ts) 在每次 unlink/rmdir 前后核对目录链、文件身份/版本、hash、实际名称及缺失结果。没有递归删除、全局文本定位、时间戳过期解锁或从日志拼接任意路径。沿用应用私有目录的协作进程威胁边界；不是对同一系统用户恶意并发改写提供原子防护的承诺。

原记录仍受 200 MiB、根目录 512 项和单文件上限约束。唯一额外空间是最多 2 MiB 的清理 manifest；清理时最多枚举 513 个根条目，以允许在原额度用满时写入这份清单。磁盘连这份有界清单也无法写入时，不能绕过确认或删除门槛。没有解除普通存储额度。

## 中断与结束

重新启动只接受完整、严格有效且仍绑定原目录的 manifest。剩余文件必须恰好是固定删除顺序的一个后缀；每个现存文件的身份、版本、hash 与清单一致。中间缺口、同内容改写、目录替换、新文件、外来锁和部分清单都被拒绝。再次检查与取消不写入；用户重新确认后才继续删除剩余项，不自动续做。

同一个已接受 commit 共享同一结果，不能重复启动。原生关闭等待已接受的清理；确认并开始后 renderer 丢失不会撤销 Main 已接受的决定。正常完成后才允许后续打开/编辑/保存。

| 结果 | 行为 |
| --- | --- |
| 未开始删除的 failed/cancelled | 本次不继续删除，当前剩余证据保持不变；修正条件后可以重新检查 |
| unknown | 可能已经删除一部分；保留磁盘剩余项、当前窗口及 Main 内存计划，阻止新操作和成功退出 |
| cleared 且无警告 | 原清单已核验清完，允许后续操作；已删记录不可恢复 |
| cleared 且有收尾警告 | 删除本身已确认，但收尾未正常结束；即使私有目录和 manifest 已为空，也保留窗口和内存证据，不能宣称磁盘记录仍全部存在 |

部分/损坏 manifest 的处置、活动未知会话解除冻结、通用遗留锁处理和保留部分历史的选择性清理仍未交付。不得手工删除未知证据来让普通写入或测试通过。

## 验证边界

[存储测试](../tests/unit/record-cleanup.test.mjs) 覆盖多会话 v2 历史、退役锚点、完整 Save/compaction 处置凭证顺序、真实 20 项配额释放及 Windows 保存、准备取消零写入、三处真实进程强杀、后缀验证、部分/改写/歧义反例和最终警告。原 HTML 与 CSS 使用独立完整字节/hash 核对。

`npm run test:product-cleanup` 使用 [真实 Electron 子进程](../tests/product/cleanup-child.ts) 和 [独立父进程断言](../tests/product/cleanup.test.mjs)，通过产品菜单、实际文字输入、全选复核和 Diff 保存验证 14 组流程。包括 profile 竞争、原生关闭等待、renderer 丢失、三个 Main 强杀点后的新确认、未知/警告保留，以及额度满后另存草稿退出、重启清理、再次编辑保存。

使用自制文件和独立测试 profile，Main 的原生选择/确认由测试回调返回。真实 Windows IME、原生对话框人工操作、维护者报告校稿、Windows 10、DPI/读屏、磁盘满和断电仍须单独验收；不由这些自动测试推定完成。具体运行结果、实际 AI 分工和失败修正记录见 [HAE-011](implementation/HAE-011.md)。
