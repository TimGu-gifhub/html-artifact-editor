# AI 主导开发流程

## 1. 责任分配

| 工作 | AI 开发工具 | 维护者 |
| --- | --- | --- |
| 范围与架构 | 整理选项、指出风险、提供可验证方案 | 决定取舍与是否扩大支持范围 |
| 代码与验证 | 按 Issue 实现、运行测试、修复、整理证据 | 复核关键边界和用户效果 |
| 产品设计 | 根据交互合同形成视觉选项并实现选定稿 | 选择方案、完成真实校稿验收 |
| 平台与发布 | 构建、检查、准备可审查产物 | 提供实机/签名条件，决定公开版本 |

AI 的开发速度以有效的验证闭环衡量，不以生成文件数、代码行数或并发模型数量衡量。

### 前端模型分工（2026-09-08 补充）

按维护者要求，**前端设计与实现使用 Kimi 最新正式可用模型**。本次核对的基线为 **Kimi K3**，Kimi Code 完整 CLI 别名为 `kimi-code/k3`；之后每项前端任务启动前重新核对，不能把 K3 永久当作“最新”。模型依据见 [Kimi K3 官方说明](https://www.kimi.ai/blog/kimi-k3) 和 [Kimi Code 模型配置文档](https://moonshotai.github.io/kimi-code/en/configuration/config-files)。

| 工作范围 | 执行安排 | 交付边界 |
| --- | --- | --- |
| UI 方案、React 组件、CSS、响应尺寸、交互状态与可访问性 | Kimi 最新正式可用模型；当前基线 K3 | 遵循已选视觉稿和交互合同，交付可运行前端与相应验证 |
| 混合任务中的前端部分 | Kimi，先限定文件与接口 | 包括 HAE-005/007/008/009/011/014 中涉及 UI 的部分；不因任务领域标签而绕过模型要求 |
| 源码映射、Patch、文件事务、权限与进程隔离 | 当前主开发代理 | 维护核心不变量，提供稳定的前端调用合同 |
| 集成、独立代码复核与整体验证 | 当前主开发代理，维护者完成视觉/实机验收 | 对照实际 diff 和运行结果复核，不以模型自评代替验收 |

Kimi 用于开发过程，应用仍采用既定 React/TypeScript 技术栈并保持离线运行；不为这一分工接入应用内 AI API。已有 HAE-001 工具链壳保留，后续前端改动按本规则执行，不因模型分工重写已完成的无关内容。

**每次开工的选择规则：**

1. 核对官方模型公告、模型目录和当前 Kimi Code 的可用列表，选择已正式发布且当前账号可调用的最新 Kimi 模型；预览/实验版不自动替代正式版。
2. 确认完整 CLI 别名与实际服务端 model，不使用未经验证的简称或仅凭 `latest` 字样判断。当前 `kimi-code/k3` 对应 `k3`；`kimi-for-coding` 等别名不能仅因名称包含 coding 就视为同一个模型。
3. 记录核对日期、Kimi Code CLI 版本、完整别名/实际模型和采用的推理设置；同一任务内保持一致，新模型在下一项任务开始时复核。
4. 若指定模型不可用，报告原因并继续可独立推进的核心/文档工作；前端任务保留待执行状态。未经维护者选择，不静默改用旧 Kimi 或其他提供方，也不把主代理生成的 UI 标为 Kimi 产物。

**交接与验证：** 主代理先给出任务目标、选定视觉参考、允许修改路径、接口及完整交互验收条件，再由 Kimi 完成有边界的前端任务。默认串行交接，同一时刻只有一个写入者。交付包含实际执行记录、改动文件、运行结果和未测项；主代理随后检查 diff、运行必要检查并完成集成。

当前基线的单次调用形式为 `kimi -m kimi-code/k3 -p "任务说明"`。使用前先检查本机 `kimi --help` / `kimi doctor` 及模型配置；不依靠混用提示模式与自动/计划模式来绕过交互约束。命令示例不代表本次已运行了生成任务。

### AI 使用说明与致谢维护

每次向 GitHub 推送代码或文档、提交 PR 或发布版本前，核对本次实际使用的 AI。若新增 AI 工具、模型（含新版本）或提供方，必须在同次提交中更新 [README 的 AI 辅助开发与致谢](../README.md#ai-辅助开发与致谢)，注明工具、能够核实的模型名称/版本、对应公司及实际参与范围，并致谢相应公司与模型。

仅列出实际参与本项目的 AI；配置存在或计划使用不算实际使用。无法确认具体版本时如实记录已知工具或模型系列，不猜测版本。保留已有贡献的致谢，使用记录与证据按现有隐私规则脱敏；前端模型分工和应用离线边界继续适用。

## 2. 每个任务的工作循环

1. 读取 [AGENTS.md](../AGENTS.md)、对应 Issue、依赖和当前工作区。先说明该任务将交付的可见行为。
2. 识别允许改动的模块、必须保留的不变量及最低验证方法；先复现问题或建立最小实验。
3. 完成一个可运行的小切片。优先解决源码准确性、文件安全与状态问题，再扩展界面细节。
4. 运行适合风险的检查：核心字节与保存路径必须测；纯文案改动不添加镜像测试。
5. 检查 diff、测试结果和用户路径。发现超出范围的需求登记为后续问题，不顺手实现。
6. 记录已具备、未具备、风险和证据，提交小范围 PR。人工步骤保持未验收直到真实完成。

若依赖未满足，只能执行不依赖它的有限实验，不能以临时关闭沙箱、全页序列化或跳过冲突检查让 UI 看似跑通。

## 3. 任务卡合同

每张任务卡包含任务 ID、目标、依赖、模块、产物、可观察验收条件、相关测试 ID 和退出条件。GitHub Issue 是执行状态入口；[任务 JSON](backlog.json) 与 [任务清单](BACKLOG.md) 保存可追溯的规划基线，修改范围时同步。

建议一次专注于 0.5–1 天以内能检验的切片；较大的源码映射、事务、跨平台任务先按独立实验分段。每个实验失败都提供反例，不能只报告“还在优化”。超过两轮无法可靠解决的核心假设，更新风险与范围，再继续。

PR 面向未读过聊天记录的贡献者：说明触发问题、最终行为、必要技术取舍和验证。不要贴入私人聊天、路径、账号凭据或用户原始 HTML。并发协作仅在明确安排时进行，并约定文件所有权；核心契约变更先协调。

## 5. 人工验收检查点

- M1：看到最小链路与对应字节 Diff，理解哪些节点被拒绝。
- M2：维护者自己完成脱敏报告校稿、取消、保存、撤销与恢复。
- M3：分别在 Windows 与 Apple Silicon Mac 验证安装、IME、权限和文件流程。
- M4：用真实新样例验证限制文案、错误恢复和连续使用体验。

人工验收与新增发布权限需要明确记录。当前用户授权创建这个公开 MIT 仓库，不等于将来任意版本、用户文件、凭据或付费服务都可自动发布。
