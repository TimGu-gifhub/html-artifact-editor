# AI 主导开发流程

## 1. 责任分配

| 工作 | AI 开发工具 | 维护者 |
| --- | --- | --- |
| 范围与架构 | 整理选项、指出风险、提供可验证方案 | 决定取舍与是否扩大支持范围 |
| 代码与验证 | 按 Issue 实现、运行测试、修复、整理证据 | 复核关键边界和用户效果 |
| 产品设计 | 根据交互合同形成视觉选项并实现选定稿 | 选择方案、完成真实校稿验收 |
| 平台与发布 | 构建、检查、准备可审查产物 | 提供实机/签名条件，决定公开版本 |

AI 的开发速度以有效的验证闭环衡量，不以生成文件数、代码行数或并发模型数量衡量。

## 2. 每个任务的工作循环

1. 读取 [AGENTS.md](../AGENTS.md)、对应 Issue、依赖和当前工作区。先说明该任务将交付的可见行为。
2. 识别允许改动的模块、必须保留的不变量及最低验证方法；先复现问题或建立最小实验。
3. 完成一个可运行的小切片。优先解决源码准确性、文件安全与状态问题，再扩展界面细节。
4. 运行适合风险的检查：核心字节与保存路径必须测；纯文案改动不添加镜像测试。
5. 检查 diff、测试结果和用户路径。发现超出范围的需求登记为后续问题，不顺手实现。
6. 记录已具备、未具备、风险和证据，提交小范围 PR。人工步骤保持未验收直到真实完成。

若依赖未满足，只能执行不依赖它的有限实验，不能以临时关闭沙箱、全页序列化或跳过冲突检查让 UI 看似跑通。

## 3. 任务卡合同

每张任务卡包含任务 ID、目标、依赖、模块、产物、可观察验收条件、相关测试 ID 和退出条件。GitHub Issue 是执行状态入口；[任务 JSON](backlog.json) 与 [任务清单](BACKLOG.md) 保存可追溯的规划基线，修改范围时同步。

建议一次专注于 0.5–1 天以内能检验的切片；较大的源码映射、事务、跨平台任务先按独立实验分段。每个实验失败都提供反例，不能只报告“还在优化”。超过两轮无法可靠解决的核心假设，更新风险与范围，再继续。

## 4. 交接模板

```text
任务 ID / 基线 commit：
本次目标与涉及模块：
已完成行为：
验证命令、结果和证据：
未完成或未验收项：
已知风险与降级行为：
下一条可执行步骤：
```

PR 面向未读过聊天记录的贡献者：说明触发问题、最终行为、必要技术取舍和验证。不要贴入私人聊天、路径、账号凭据或用户原始 HTML。并发协作仅在明确安排时进行，并约定文件所有权；核心契约变更先协调。

## 5. 人工验收检查点

- M1：看到最小链路与对应字节 Diff，理解哪些节点被拒绝。
- M2：维护者自己完成脱敏报告校稿、取消、保存、撤销与恢复。
- M3：分别在 Windows 与 Apple Silicon Mac 验证安装、IME、权限和文件流程。
- M4：用真实新样例验证限制文案、错误恢复和连续使用体验。

人工验收与新增发布权限需要明确记录。当前用户授权创建这个公开 MIT 仓库，不等于将来任意版本、用户文件、凭据或付费服务都可自动发布。
